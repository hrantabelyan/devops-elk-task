# ELK + Apache on Azure

Two Ubuntu 24.04 VMs on Azure. One runs a hardened Apache web server and ships its logs with Filebeat; the other runs Elasticsearch, Logstash and Kibana, receives those logs and shows them on a dashboard. A single `terraform apply` builds everything: Terraform creates the infrastructure, then its `local-exec` provisioner runs Ansible, which installs and configures the ELK stack, Apache and Filebeat. The Elastic Stack passwords live in Azure Key Vault. GitHub Actions checks every pull request and push to `main`.

## Goal

| Component | Requirement |
| --- | --- |
| Web server (`web`) | Apache on HTTPS, all HTTP redirected to HTTPS, `ServerTokens` and `ServerSignature` disabled. Filebeat ships Apache access and error logs to the ELK node. |
| Logging server (`elk`) | Elasticsearch, Logstash and Kibana. Ports 5044 and 9200 accept traffic only from the web server's private IP. |
| Dashboard | Kibana dashboard showing HTTP status codes, access logs and error logs. |

## Architecture

```
            Azure, Sweden Central, zone 1 · resource group devops-bank
          devops-bank-dev-vnet 172.16.0.0/16 · devops-bank-dev-snet 172.16.0.0/24

  web  devops-bank-dev-web                  elk  devops-bank-dev-elk
  172.16.0.11 · Standard_D2ls_v5            172.16.0.12 · Standard_B4as_v2
  +----------------------------+            +----------------------------+
  | Apache  :80 -> :443        |    5044    | Logstash       :5044       |
  | Filebeat                   | ---------> | Elasticsearch  :9200       |
  |                            |            | Kibana         :5601       |
  +----------------------------+            +----------------------------+
  inbound: 80, 443 from anywhere            inbound: 5044, 9200 from web
           22 from your IP                           22, 5601 from your IP
```

What `terraform apply` does, in order:

```
terraform apply
  ├─ Azure: VNet, subnet, NSGs, public IPs, VMs
  ├─ Key Vault  → elastic, kibana_system, logstash_internal passwords in devops-bank-dev-kv (never stored in Terraform state)
  ├─ SSH key    → ansible/.ssh/id_ed25519
  ├─ inventory  → ansible/inventory.ini (IPs, ports, key path, Key Vault name from what Terraform created)
  └─ terraform_data.ansible, local-exec provisioner
       └─ ansible-playbook site.yml
            ├─ read the passwords from Key Vault with the Azure CLI
            ├─ wait for SSH and cloud-init on both VMs
            ├─ elk: install Elasticsearch, Logstash, Kibana; import the dashboard
            └─ web: install Apache with HTTPS and a Let's Encrypt certificate; install Filebeat
```

IPs, keys and passwords are never copied by hand: Ansible reads the inventory and key Terraform just wrote, and the passwords from Key Vault.

## Prerequisites

- Azure CLI, logged in (`az login`) as the account that runs Terraform and Ansible: a dedicated DevOps account, not an Owner
- Terraform 1.11 or later
- ansible-core 2.17 or later on the machine running Terraform: `terraform apply` runs the playbook
- curl and jq, for the commands below
- The Key Vault `devops-bank-dev-kv` and these roles for the DevOps account, set up once by an admin (below):

| Role | Scope | Needed for |
| --- | --- | --- |
| Network Contributor | resource group `devops-bank` | VNet, subnet, NSGs and rules, public IPs, network interfaces |
| Virtual Machine Contributor | resource group `devops-bank` | VMs and their OS disks, attaching them to the network |
| Storage Blob Data Contributor | storage account `tfstate20260914` | Terraform state (container `tfstate`) |
| Key Vault Secrets Officer | Key Vault `devops-bank-dev-kv` | Terraform writes the stack passwords, Ansible reads them |

None of these roles can assign roles or read anything outside its scope. Here the first three come through Entra ID groups the DevOps account is a member of, and the last one is assigned to it directly. After any role change, run `az logout` and `az login` again, and allow a few minutes for it to apply.

### One-time setup by an admin

The DevOps account can create resources but can't assign roles, so an admin grants them once. The resource group, the state storage account and the Key Vault are created outside Terraform too.

Let a group the DevOps account belongs to build the resources in `devops-bank`. `<group-object-id>` is that group's object ID. Use these roles, not the "Classic" ones with similar names: those only cover Azure's retired classic deployment model.

```bash
az role assignment create --assignee-object-id "<group-object-id>" --assignee-principal-type Group --role "Network Contributor" --scope "$(az group show --name devops-bank --query id -o tsv)"
```

```bash
az role assignment create --assignee-object-id "<group-object-id>" --assignee-principal-type Group --role "Virtual Machine Contributor" --scope "$(az group show --name devops-bank --query id -o tsv)"
```

The Key Vault holds the stack passwords. Terraform looks it up by name (`local.key_vault_name`, `devops-bank-dev-kv`) and manages only the three secrets in it.

Register the Key Vault resource provider, only if the subscription has never had a vault (`providers.tf` turns off automatic registration):

```bash
az provider register --namespace Microsoft.KeyVault
```

Create the vault with Azure RBAC access, a public endpoint and no purge protection:

```bash
az keyvault create --name devops-bank-dev-kv --resource-group devops-bank --location israelcentral --enable-rbac-authorization true
```

Let the account that runs Terraform and Ansible read and write its secrets. `<account>` is its sign-in name, or its app ID for a service principal:

```bash
az role assignment create --assignee "<account>" --role "Key Vault Secrets Officer" --scope "$(az keyvault show --name devops-bank-dev-kv --query id -o tsv)"
```

Owner or Contributor alone doesn't allow reading secrets: Key Vault data access is a role of its own. A new role assignment can take a few minutes to apply.

## Provision the infrastructure

Run these from `terraform/envs/dev`:

```bash
cd terraform/envs/dev
```

Log in and select the subscription:

```bash
az login
```

```bash
export ARM_SUBSCRIPTION_ID=$(az account show --query id -o tsv)
```

Allow your public IP for SSH and Kibana (format as in `terraform.tfvars-example`):

```bash
echo "operator_ip = \"$(curl -s https://api.ipify.org)/32\"" > terraform.tfvars
```

If you connect through a VPN, run it while connected: Azure sees the VPN's exit IP, so that is the address the NSGs must allow. When it changes, update `terraform.tfvars` and run `terraform apply`, which updates only the NSG rules.

Initialise. State is stored in Azure Storage under `elk/dev/terraform.tfstate`:

```bash
terraform init
```

Review the changes, then apply. Apply creates the VMs, then the `local-exec` provisioner in `ansible.tf` runs `ansible-playbook site.yml`, which installs the ELK stack on `elk` and Apache and Filebeat on `web`. The Ansible output streams into the apply output and the whole run takes several minutes. If the playbook fails, the VMs stay and the next `terraform apply` runs it again:

```bash
terraform plan
```

```bash
terraform apply
```

Connect to the VMs:

```bash
terraform output ssh_commands
```

Tear everything down:

```bash
terraform destroy
```

## Configure the servers

`site.yml` first waits for SSH and cloud-init on both VMs, then runs these roles in this order:

| Role | Hosts | Responsibility |
| --- | --- | --- |
| `elk` | `elk` | Elasticsearch, Logstash and Kibana 9.5.4 bound to the private IP, Elasticsearch TLS and built-in passwords, Logstash Beats input on 5044; ends by checking health and listening addresses |
| `kibana_dashboard` | `elk` | "Apache web server" dashboard: HTTP status codes over time, requests by status code, access logs, error logs; imported when Kibana differs from the export in git |
| `apache` | `web` | HTTPS vhost with a Let's Encrypt certificate for the public IP from certbot, which also renews it; HTTP to HTTPS redirect, `ServerTokens Prod`, `ServerSignature Off`; ends by checking all of them on the server |
| `filebeat` | `web` | Filebeat 9.5.4 apache module shipping access and error logs to Logstash on `elk` port 5044; loads the module's ingest pipelines; ends by finding a test request, parsed, in Elasticsearch |

Ansible runs on your machine and changes the VMs over SSH. Nothing is installed on the VMs to receive it:

```
your machine (ansible-playbook)
  ├─ HTTPS 443 → Key Vault          first play: az keyvault secret show ×3, as your az login
  └─ SSH 22    → web and elk VMs    public IPs from the inventory, user azureuser, key ansible/.ssh/id_ed25519;
                                    the NSGs accept port 22 only from operator_ip; tasks run with sudo
web VM (Filebeat) → elk VM (Logstash 5044)   private network, inside the VNet
```

The generated inventory has the groups `web` and `elk`, a `private_ip` host variable, and `<service>_port` variables matching the NSG rules. The key file is only there while the infrastructure exists: `terraform destroy` removes it. Ansible keeps the VMs' host keys in `ansible/.ssh/known_hosts`, which Terraform clears before it runs the playbook, because new VMs can get public IPs that older VMs had.

The Terraform provisioner runs the playbook only when a VM is created or replaced, or the inventory changes. After changing a role, run it yourself from `ansible/`:

```bash
cd ansible
```

Install the collections the roles need:

```bash
ansible-galaxy collection install -r requirements.yml
```

Configure both servers:

```bash
ansible-playbook site.yml
```

Re-run a single role with its tag, for example only Filebeat:

```bash
ansible-playbook site.yml --limit web --tags filebeat
```

- The site is at `https://<web public IP>`, with the IP from `terraform output public_ips`, and the browser trusts the certificate.
- Kibana is at `http://<elk public IP>:5601` from your IP. Log in as `elastic` with the password from Key Vault:

```bash
az keyvault secret show --vault-name devops-bank-dev-kv --name elastic-password --query value -o tsv
```

- The dashboard is at `http://<elk public IP>:5601/app/dashboards#/view/apache-web-server`.

### TLS certificate

certbot on the web server gets the certificate and renews it. Ansible only asks for one when the server has none, or when the one it has is for a different IP.

- Let's Encrypt issues certificates for IP addresses only with the `shortlived` profile: valid for 160 hours, about 6.7 days.
- certbot comes from snap. Ubuntu's package is far older than 5.4, the first certbot whose webroot plugin can validate an IP address. The role passes `--agree-tos`, which accepts the [Subscriber Agreement](https://letsencrypt.org/repository/).
- Validation uses `http-01` on port 80. The port 80 vhost serves `/.well-known/acme-challenge/` and redirects everything else to HTTPS.
- Apache serves only port 80 until the certificate exists; the HTTPS vhost is enabled right after certbot writes it. If issuing fails, the playbook stops and the site has no HTTPS until a later run succeeds.
- **Renewal needs no playbook run.** `snap.certbot.renew.timer` fires twice a day, renews once the certificate is about two thirds through its life, and reloads Apache through the `renew_hook` in `/etc/letsencrypt/renewal/<host>.conf`. The role adds `Persistent=true` to the timer, so a VM that was stopped over a scheduled run renews at boot instead of waiting for the next one.
- Check renewal on the web server, which uses the staging environment and leaves the live certificate alone:

```bash
sudo certbot renew --dry-run
```

- To issue from staging while testing, set `apache_certbot_extra_args: ["--test-cert"]`. Staging certificates are not trusted by browsers.

### Kibana dashboard

The dashboard lives in git as a Kibana export, `ansible/roles/kibana_dashboard/files/apache-web-server.ndjson`: one data view (`filebeat-*`), two Lens charts, two saved searches and the dashboard. On every run the role exports the dashboard from Kibana, compares it with this file (ignoring per-instance fields such as timestamps) and re-imports the file when they differ. It comes back after every rebuild, and edits made only in the Kibana UI are overwritten.

To change it, edit the dashboard in Kibana, save, then export it over the file from `ansible/` before the next playbook run. Read the `elastic` password first:

```bash
ELASTIC_PASSWORD=$(az keyvault secret show --vault-name devops-bank-dev-kv --name elastic-password --query value -o tsv)
```

```bash
curl -s -u "elastic:$ELASTIC_PASSWORD" -H 'kbn-xsrf: true' -H 'Content-Type: application/json' -X POST "http://<elk public IP>:5601/api/saved_objects/_export" -d '{"objects":[{"type":"dashboard","id":"apache-web-server"}],"includeReferencesDeep":true,"excludeExportDetails":true}' | jq -c 'del(.updated_at, .created_at, .version, .updated_by, .created_by)' > roles/kibana_dashboard/files/apache-web-server.ndjson
```

## Secrets in Key Vault

The Elastic Stack passwords (`elastic`, `kibana_system`, `logstash_internal`) live in the Key Vault `devops-bank-dev-kv` as `elastic-password`, `kibana-system-password` and `logstash-internal-password`, so every machine that runs the playbook uses the same ones.

- **Generated by Terraform, never stored by it.** `secrets.tf` makes each password with an `ephemeral` resource and writes it with the secret's write-only `value_wo` argument, so neither the plan nor the state holds it.
- **Read once per run.** The first play in `site.yml` reads the three secrets with the Azure CLI, as the account you are logged in with, and sets them on every host. A missing `az login`, role or secret stops the run there, before any server changes.
- **Rotate** a password by bumping its number in `stack_passwords` in `terraform/envs/dev/locals.tf`, then run `terraform apply` and the playbook. The apply alone doesn't start the playbook. The `elk` role finds that the old password no longer works and sets the new one on the cluster.
- **Destroy** deletes and purges the three secrets, and keeps the vault. The next apply writes new ones.

Passwords used to be generated into `ansible/.secrets/`. Nothing reads that folder any more, so it can be deleted.

## CI

`.github/workflows/ci.yml` runs on every pull request into `main`, every push to `main`, and on demand from the Actions tab. It only checks the code: there is no Azure login and no secrets, and nothing is planned or deployed. Changes to Markdown files alone don't start it.

| Job | Checks |
| --- | --- |
| Terraform quality | `terraform fmt -check -recursive`, then `terraform init -backend=false` and `terraform validate` in `terraform/envs/dev` |
| Ansible quality | `ansible-lint` in `ansible/`, which also runs the playbook syntax check (ansible-core 2.21.4, ansible-lint 26.10.1) |
| Security scan | Checkov 3.3.22 on Terraform, Ansible, the workflows, and every file for leaked secrets, with the settings in `.checkov.yaml` |
| Workflow quality | `actionlint` on the workflow files, including shellcheck on their scripts |

Run the same checks locally before pushing. From the repository root:

```bash
terraform fmt -check -recursive terraform
```

From `ansible/`:

```bash
ansible-lint
```

From the repository root. Checkov reads `.checkov.yaml`, which skips gitignored local files such as `ansible/.secrets/` and the Terraform state:

```bash
checkov
```

Checkov findings that are intended are suppressed next to the code, with the reason, as the first line inside the Terraform resource or Ansible task:

```hcl
# checkov:skip=CKV_AZURE_119: both VMs need a public IP: web serves the site, elk takes SSH and Kibana from the operator IP
```

Any other finding fails the job. One check, `CKV2_ANSIBLE_3` (a block without `rescue`), is skipped in `.checkov.yaml` instead, because Checkov ignores skip comments on blocks.
